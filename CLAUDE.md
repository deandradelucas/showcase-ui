# CLAUDE.md — showcase-ui

Porta dev: 4320. Next.js 16 + React 19 + TypeScript + Tailwind v4 + shadcn/ui (preset Nova, base Base UI).

Esta versão do Next.js pode ter breaking changes vs. o que já está no treino do modelo. Checar `node_modules/next/dist/docs/` antes de assumir comportamento.

shadcn/ui aqui roda sobre **Base UI**, não Radix — diferenças de API confirmadas na prática:
- Composição: `render={<Elemento />}`, não `asChild`.
- `Toast`: precisa `<Toaster>` envolvendo o layout raiz (mesmo padrão do `TooltipProvider`); disparar com `toast.add({...})`, não `toast({...})` — `toast` é uma instância de `ToastManager`, não uma função.
- `Accordion`: usa `multiple={false}` pra modo single-open, não `type="single" collapsible` (isso é API do Radix).
- `Select`: `SelectValue` mostra o `value` bruto do item selecionado (ex.: `"pro"`), não o label renderizado — diferente do Radix, que resolve isso sozinho. Precisa passar `items={[{value, label}]}` no `Select` (ou função `children={(value) => label}` na `SelectValue`) pra mostrar o texto certo.
- `Resizable` (react-resizable-panels, não Base UI): usa `orientation="horizontal"|"vertical"` no `ResizablePanelGroup`, não `direction` (API antiga da lib).

**Convenção do projeto:** todo elemento clicável ganha `cursor-pointer` explícito — o preset Nova não traz isso por padrão, e alguns (`SelectItem`, `DropdownMenuItem` e afins) vêm com `cursor-default` de propósito (estilo menu nativo), mas aqui trocamos pra pointer. Já aplicado em: `Button`, `Checkbox`, `Switch`, `Tabs`/`Accordion`/`Menubar` (trigger), `Toggle`/`ToggleGroup`, `RadioGroup`, `Slider` (thumb), `NativeSelect`, `Sidebar` (menu button + actions), `Select`/`Command`/`ContextMenu`/`DropdownMenu` (item, sub-trigger, checkbox/radio item). Elemento `<a>` (BreadcrumbLink, PaginationLink, NavigationMenuLink) não precisa — âncora já tem pointer nativo. Todo componente clicável novo deve seguir a mesma convenção.

**Convenção do projeto:** toda página de demo dedicada (uma página = um componente/padrão, ex. `device-iphone`, `chart-barra`, `hover-card`) precisa ter o botão `View Code` (`components/view-code.tsx`), nunca bloco de código exposto sem modal. Padrão: página server component (`async`), lê o source real do arquivo com `readComponentSource` (`lib/read-source.ts`) — nunca copiar/colar código à mão numa string —, monta os arquivos com `buildCodeFiles` (`lib/view-code-files.ts`, aplica syntax highlight via shiki) e passa pro `<ViewCode install="..." files={files} />`. Posição fixa: dentro do `CardHeader`, envolto em `<CardAction>` (`components/ui/card.tsx`), nunca dentro do `CardContent` junto da demo — fica no canto superior direito, ao lado do título. O `install` usa `deandradelucas/showcase-ui/<item>` só quando o componente é autoral e está em `registry.json`; se a página demonstra um componente stock do shadcn (ex. `hover-card`, `chart`) o comando é o oficial (`add hover-card`, `add chart`), nunca republicar sob o nosso registry. Se a página precisa ser client component (ex. Recharts), isolar a parte client num arquivo à parte em `components/demos/` e manter a página em si como server component, senão `readComponentSource` não funciona (é `fs`, só roda no servidor). No `CardHeader`: `CardTitle` — sem `CardDescription` no card — leva um sufixo com a origem do componente quando ele vem de fora do shadcn (ex. `Android — MagicUI`, `Chart (Barra) — Recharts`); componente stock do shadcn/Base UI (ex. Hover Card) não leva sufixo. A frase explicativa que antes ficava embaixo do título vira o `description` do `<ViewCode>` (aparece no modal, abaixo de "Installation"). `CardHeader` sempre com `className="border-b"` — separa visualmente o título do preview, usando o mecanismo que já existe em `card.tsx` (`[.border-b]:pb-(--card-spacing)`). Essa regra vale pras páginas de demo dedicadas; a vitrine grande em `/componentes` (primitivos shadcn soltos) está fora do escopo por ora.

**Cuidado com `npx shadcn add -o` (overwrite):** sobrescreve QUALQUER arquivo customizado que apareça como dependência de um componente novo, mesmo sem intenção — já aconteceu duas vezes nesta sessão com `button.tsx`/`dropdown-menu.tsx` voltando pro stock (perdendo `cursor-pointer`). Depois de qualquer `add -o`, rodar `git diff --stat components/ui/` e conferir se algum arquivo customizado voltou ao original antes de commitar.

**Registry publicável:** `registry.json` na raiz registra os componentes autorais (`mode-toggle`, `app-sidebar`, `registry-auth`) como `registry:ui`/`registry:lib`. Componente autoral usado dentro de outro item entra na lista `files` dele, nunca em `registryDependencies` (gotcha confirmado no projeto anterior: nome sem namespace em `registryDependencies` sempre resolve contra o registry oficial do shadcn, nunca contra o próprio — `app-sidebar` inclui `mode-toggle.tsx` direto nos `files`).

**Repo GitHub público desde 01-08-2026** (`docs/registry/github` — repositório privado não é suportado como registry). Isso significa que o registry existe em **dois canais paralelos**, com segurança diferente:
- `npx shadcn add deandradelucas/showcase-ui/<item>` — lê os arquivos direto do GitHub (raw), **sem passar pela nossa auth em nenhum momento**. Testado: `registry validate`, `list` e `add` de verdade, tudo funcionando sem servidor rodando.
- `npx shadcn add @showcase-ui/<item>` apontando pro `.mcp`/rota Next.js — passa pelo `REGISTRY_TOKEN` se configurado.

**Ou seja: `REGISTRY_TOKEN` não protege o conteúdo de verdade**, já que o mesmo `registry.json`/arquivos estão públicos no repo GitHub de qualquer forma. Auth só faz sentido real se o repo também for privado (o que quebraria o canal GitHub) — os dois mecanismos são mutuamente exclusivos na prática, não complementares. Registrado aqui pra não achar no futuro que o token protege algo que não protege.

**MCP:** `.mcp.json` configurado (`npx shadcn@latest mcp init --client claude`) — dá acesso ao registry oficial do shadcn via protocolo MCP. Precisa reiniciar o Claude Code pra ativar nesta sessão.

**Package Imports / Monorepo:** não aplicáveis — projeto usa alias `@/` do `tsconfig.json` (não `#` do `package.json#imports`, que só faz sentido em monorepo), e é app único, sem `apps/`+`packages/`.

**Dynamic Search (registry):** implementado a pedido explícito do usuário, mesmo com só 2 itens no registry (não era necessário pelo critério da doc — "milhares de itens" — mas ele quis de qualquer forma). `app/r/registry.json/route.ts` lê `registry.json` do disco, filtra por `q`/`type`, pagina com `limit`/`offset`, devolve `pagination.hasMore` — testado com `npx shadcn search` de verdade contra o servidor local, funcionando.

**Gotcha real:** essa rota dinâmica conflita com o `public/r/registry.json` estático que `shadcn build` sempre gera — erro em runtime ("A conflicting public file and page file was found"), só aparece na hora da requisição, não no build. Corrigido apagando `public/r/registry.json` logo depois do `shadcn build` no script `registry:build` (`node -e "require('fs').rmSync(...)"`); os itens individuais (`public/r/mode-toggle.json` etc.) continuam estáticos normalmente, só o índice virou dinâmico.

**Instalação via namespace testada de ponta a ponta** (`npx shadcn registry add "@showcase-ui=http://localhost:4320/r/{name}.json"` + `npx shadcn add @showcase-ui/app-sidebar` num app descartável), achou 2 bugs reais no `registry.json` que só apareciam no build do consumidor, nunca no `shadcn view`/`build` daqui:
- `mode-toggle` e `app-sidebar` usam `next-themes`, mas faltava declarar em `dependencies` — sem isso, `npm install` do consumidor nunca instalava o pacote.
- `app-sidebar` empacota `mode-toggle.tsx` direto em `files` (não como item próprio via `registryDependencies`), então **não herda** as dependências dele — precisou repetir `button`/`dropdown-menu` no `registryDependencies` do próprio `app-sidebar`.
- Regra geral confirmada: sempre testar um item com `add` de verdade num app novo (não só `view`/`search`), porque erro de dependência faltando só aparece no `npm run build` do lado de quem instala.

**Authentication (registry):** implementado a pedido explícito do usuário (`docs/registry/authentication`), mesmo o registry sendo público hoje. Token bearer opcional via `REGISTRY_TOKEN` (`.env.example`) — sem a env var, registry fica público (default de dev); com ela, `/r/registry.json` e `/r/[name]` exigem `Authorization: Bearer <token>` ou devolvem 401. Testado com curl nos 3 cenários (sem header, token errado, token certo) e com `npx shadcn add` de verdade contra o servidor sem token (público).

Isso forçou trocar a distribuição dos itens de estático pra dinâmico: `npm run registry:build` agora manda o output pra `.registry-build/r/` (fora de `public/`, via `shadcn build --output`), e `app/r/[name]/route.ts` lê de lá e serve sob demanda — porque um arquivo estático em `public/` não tem como respeitar header de auth, o servidor entrega ele direto. `public/r/` foi removido de vez do projeto.

**Gotcha do segmento dinâmico:** Next.js não aceita pasta `[name].json` (bracket + sufixo literal no mesmo segmento) — só `[name]` sozinho. Precisou renomear a pasta pra `app/r/[name]/route.ts` e tirar o `.json` do `name` recebido manualmente (`name.replace(/\.json$/, "")`) dentro do handler.

**Registry externo `registry.watermelon.sh` tem bugs reais e recorrentes** (confirmado instalando 30+ itens). Checklist obrigatório depois de QUALQUER `npx shadcn add` desse registry, antes de dar como concluído:
1. Nome do item errado na URL devolve HTML (SPA fallback) com HTTP 200, não 404 — `npx shadcn add` falha com "Unexpected token '<'". Conferir o nome certo em `curl .../r/registry.json` (grep pelo termo) antes de reportar item inexistente.
2. `dependencies` do registry vem incompleta ou errada com frequência: pacotes reais faltando (`react-icons`, `react-use-measure`, `@hugeicons/react`+`@hugeicons/core-free-icons`, `@number-flow/react` já vistos faltando); um item declarou `"motion/react"` como se fosse pacote npm — isso quebra `npm install` (erro de git/GitHub) e o `add` nem chega a escrever o arquivo, precisa baixar o JSON na mão (`curl .../r/<item>.json`) e extrair `files[0].content` via `python3 -c "import json..."`. Sempre comparar os imports do arquivo final com `package.json`.
3. Vários itens importam de `"framer-motion"` no código apesar do registry declarar `motion` — trocar o import pra `"motion/react"` (o pacote `framer-motion` nunca é instalado aqui).
4. `oklch(var(--foreground)/0.1)` (ou qualquer `hsl(var(--x)/N)`) é CSS inválido neste projeto — as variáveis de tema já são um valor `oklch(...)` completo, não os componentes L/C/H soltos, então embrulhar de novo quebra silenciosamente (o browser ignora o valor). Aparece em `shadow-[...]` do Tailwind, em `boxShadow` inline de motion, e em `<style jsx>`. Corrigir com `color-mix(in oklch, var(--x) N%, transparent)`, ou trocar por uma classe Tailwind pronta (`shadow-sm`/`shadow-md`/`shadow-lg`) quando o efeito for só decorativo.
5. Vários itens não têm `'use client'` apesar de usar hooks (`useState`/`useEffect`) — falha silenciosa até renderizar num server component.
6. Vários itens usam `h-screen`/`min-h-screen` no wrapper raiz (herdado da página de demo original deles, feita pra tela cheia) — quebra o layout dentro do nosso `Card` compacto; trocar por uma altura fixa razoável (`h-72`/`h-96`) ou remover.
7. Prop com valor default na desestruturação mas tipada como obrigatória na interface (`items: T[]` em vez de `items?: T[]`) — trava o build de TypeScript quando a página de demo confia no default. Corrigir a interface, não forçar prop no chamador.
8. Nenhum item vem com `cursor-pointer` nos elementos clicáveis (convenção do projeto) — sempre revisar todo `<button>`/`onClick` do arquivo.
9. Ocasional debug esquecido (`console.log`) e classe Tailwind com typo/duplicada (ex. `text-muted-foreground-foreground`) — ler o arquivo inteiro, não só a parte que dá erro de build.

**Registries `@animate-ui` e `@aceternity` têm o mesmo tipo de bug recorrente do watermelon**, com uma variante grave própria: em `components/animate-ui/components/**` (a camada "wrapper" que fica entre a página de demo e `components/animate-ui/primitives/**`), vários arquivos usam hook/contexto ou chamam função client-only (`getStrictContext`, `buttonVariants`) sem ter `'use client'` no topo, mesmo a primitiva correspondente tendo a diretiva. `npm run lint` e `next dev` não acusam nada — só aparece em `next build` (Turbopack e webpack, testado nos dois), e o erro (`TypeError: ... createContext is not a function` ou `Attempted to call X() from the server but X is on the client`) não aponta pro arquivo culpado, só pra rota que primeiro importa a árvore quebrada, na fase "Collecting page data"/"Generating static pages". Checklist depois de instalar qualquer item desses dois registries, antes de dar como concluído: rodar `npm run build` de verdade (não só lint/dev) e, se quebrar assim, procurar em `components/animate-ui/components/**` (ou pasta equivalente da Aceternity) por arquivo que usa hook/contexto/função client-only sem `'use client'` no topo — comparar com a lista de arquivos já corrigidos: `components/animate-ui/components/{buttons/flip,animate/tooltip,base/alert-dialog,radix/checkbox,radix/files,radix/preview-link-card,radix/sheet}.tsx`. `lib/get-strict-context.tsx` também foi tornado lazy (cria o `Context` no primeiro render, não no escopo do módulo) como reforço extra, mas a causa raiz real era a diretiva faltando.

**GSAP (`gsap`/`@gsap/react`) e classe Tailwind `transition-all`/`transition-*` não se misturam** quando ambos miram a mesma propriedade (`opacity`, `transform`) — confirmado em `components/ui/morphing-select.tsx`. O CSS `transition` do browser tenta interpolar suavemente toda vez que o GSAP escreve um novo valor inline a cada frame, e como o alvo muda constantemente, o elemento nunca alcança o valor real — fica visualmente preso perto do estado inicial (`opacity` baixa, por exemplo) mesmo com o `style` inline e a `animate()` do GSAP reportando o valor certo. Sintoma: `el.getAttribute('style')` mostra o valor correto, mas `getComputedStyle(el).opacity` fica baixo/zero. Sintoma relacionado, mas causa diferente: se o elemento some de vez (`display:none` inesperado) após abrir/fechar rápido, é o `onComplete` de uma tween antiga (não cancelada) disparando depois da nova animação já ter começado — chamar `gsap.killTweensOf(el)` no início do efeito antes de iniciar qualquer tween nova evita isso. Regra: qualquer elemento animado via GSAP não pode ter `transition`/`transition-all`/`transition-opacity`/`transition-transform` do Tailwind nas mesmas propriedades — usar `transition-colors` (ou remover a transição) quando só as cores precisam de easing via CSS.
